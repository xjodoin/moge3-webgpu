# FP16 experiment — 2026-10-31

Both FP16 modes are implemented and run locally on WebGPU. Neither meets the
existing FP32 release gate, so the UI and published demo remain FP32.
There is no retraining, pruning, architecture change or parameter-count change.

## Results

Apple M4 Pro 24 GB, Chrome 156, Metal, AC power verified throughout. Each mode
has 54 measured comparisons: three synthetic photos × two resolutions × three
refinement counts (1/2/3) × three repeats. Three warmups per configuration,
162 measured runs total. This is a small reconstruction regression set, not a
general accuracy evaluation on real-world scenes.

GB is decimal. Inference asset totals include one dense profile, the 11 active
ONNX linear/projection modules and the ten packed WGSL blocks. They exclude
goldens, photos, browser libraries and unused ONNX sparse-block alternatives.
The dense model alone is reduced from 1.325 GB to approximately 663 MB at Fast
resolution. File size is measured; network download latency is not benchmarked.

Runtime reductions are geometric means of the six matched configuration-median
ratios. The modes are grouped, with order reversed at the second resolution.
Timings include input upload, required readbacks, refinement and CPU camera
fitting; loading, validation and rendering are outside the timer. GPU counters
measure explicit WebGPU buffers, including retained pools. They exclude driver,
WebGL, browser overhead and process RSS.

All valid output values remained finite. The storage variant changed up to 43
mask pixels; the compute variant changed up to 7,447. Worst mask fractions were
0.0136% and 1.8939%, respectively (the maxima occur in different cases from the
maximum pixel counts). FP32 masks match all references. Worst camera-intrinsics
NRMSE is 0.0199% for storage and 3.5507% for computation.

The existing gate remains points/intrinsics and all six dense outputs below
0.1% NRMSE, with the existing tight mask-boundary rule. It was not relaxed to
accept FP16. Original NVIDIA strict-FP32 references were not regenerated.
Storage-only median geometry error is 0.299%; compute median error is 6.858%.
Neither measured drift nor this monocular reference comparison establishes
real-world measurement accuracy.

## Implementation

`fp16-storage` stores ONNX initializers as half precision and inserts FP32 casts
before the existing operations. ORT can expand those weights during session
optimization, so the ONNX weight reduction primarily benefits transfers and
storage. WGSL block weights stay half precision on the GPU and explicitly widen
before every FP32 normalization/FMA. Features and accumulators remain FP32.

`fp16-compute` uses the ONNX Runtime FP16 converter with FP32 model inputs and
outputs. Convertible dense/linear operations and weights use FP16. WGSL block
accumulation, voxel indexing, depth updates, geometry and camera fitting remain
FP32. Scalar/shape constants are folded in FP32 before conversion: leaving their
FP16 Sqrt/Pow nodes unfolded caused the no-CPU-fallback session gate to reject
the original conversion. Learned operations retain WebGPU execution throughout.
An additional FP32-only folding control passes all six photo/resolution checks;
all 36 dense-output error reports are identical to the unfolded FP32 control.
Constant folding itself introduced no observed additional error in these tests.

Both modes require `shader-f16`. Graph capture is disabled for this experiment;
buffer reuse, GPU indexing and the validated subgroup sparse configuration stay
enabled. Packed manifests retain layout validation, per-block SHA-256 and byte
checks, and identify FP16 storage separately from FP32. Switching precision
unloads sessions. All six unload checks retained zero sessions and no pooled
buffers. FP32 weight loading and shaders retain their existing path.

The conversion follows the [ONNX Runtime FP16 guidance](https://onnxruntime.ai/docs/performance/model-optimizations/float16.html).
Conversion scripts use the pinned export environment and refuse to overwrite
existing models. Export metadata records source hashes, target hashes and sizes.

## Reproduce locally

Export into the ignored `public/models/precision/` directory. The source FP32
models, checkpoint and independent references must already be set up.

```sh
for mode in storage compute; do
  for profile in fast detail refiner; do
    .venv/bin/python export_fp16.py --mode "$mode" --profile "$profile"
  done
done
npm run dev
```

In the developer console at `http://127.0.0.1:5180/`:

```js
await window.setPrecision('fp16-storage'); // or 'fp16-compute'
await window.runTest(true, 'sample-backyard', null, 'detail', 'wgsl', 3, true);
await window.setPrecision('fp32'); // unload and restore the default
```

For the full comparison, run a fresh power logger before starting:

```sh
.venv/bin/python benchmark_power.py results/new-fp16-power.stop > results/new-fp16-power.jsonl
```

```js
const {benchmarkFp16} = await import('/benchmark-fp16.browser.js');
const report = await benchmarkFp16(3);
```

The helper exposes `window.fp16Report` / `window.fp16Progress` while running and
restores unloaded FP32 at completion. Save the report and matching power samples
under new names to preserve this experiment. `summarize-fp16.py` validates this
saved run's coverage, AC power, original gates, hashes and unload checks; it
refuses to overwrite its summary.

Evidence: [summary](benchmarks/fp16-summary.json),
[all measured runs and warmups](benchmarks/fp16-browser.json),
[power samples](benchmarks/fp16-power.jsonl),
[FP32 folding control](benchmarks/fp16-folding-control.json).

To reproduce the folding control, export it with
`.venv/bin/python export_fp16_fold_control.py`, then run
`await (await import('/validate-fp16-folding.browser.js')).validateFp16Folding()`
in the developer console. These additional FP32 model files are local diagnostics.

Validation: 27 unit tests pass; all 54 FP32 CUDA comparisons pass. FP16 accuracy
failures are recorded, not presented as a successful release qualification.
The FP16 variants remain local experiments; the public demo defaults to FP32.
